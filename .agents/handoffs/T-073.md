# T-073 handoff: Installing an update never loses an edit

Found by Codex while reviewing T-072: "Install and restart" called the backend, which starts the installer and exits the app, without saving open documents. An edit inside the autosave delay was lost, and so was the editor's version of a note with an unresolved "changed on disk" conflict.

## What was built

- **`src/features/files/unsavedWork.ts`**, a registry of open documents:
  - `registerDocument(path, flush)`: each open note, grid, canvas and editable embed registers a function that saves now and reports what is still unsaved. A flush that throws counts as `failed`, never as saved.
  - `trackClosingWrite(path, content, write)`: runs the final write a document makes when it closes (switching notes), so `saveAll` waits for it. `write` rejects unless `content` reached the disk.
    - Notes and grids/canvases first wait for any save already under way, then write only if still needed, using the current mtime.
    - If the write fails, `content` is kept in a new file next to the original, `Name (unsaved YYYY-MM-DD HH-MM-SS).ext`. It is created with `createFile`, so it never overwrites, and gets a numbered suffix if the name is taken. The user is told the name in the error banner.
    - Each document passes the vault it was loaded from (`currentVault()` at load). Nothing is written, neither the final write nor the recovery file, while another vault is open. Opening a vault switches the backend before the old editor unmounts, so without this a closing note could be written into the new vault. If the recovery file can't be created (another vault is open, or the disk fails), `saveAll` tries again each time and reports the file as `failed` until it works.
  - `preserveEdits(on)`: while installing, an embed save that finds its source block changed keeps the edit and reports it. This includes a save already under way when Install was clicked (the blur save).
  - `saveAll()`: runs every flush, waits for the closing writes and retries recovery files not yet written. It returns the documents still not on disk, one per path, with a reason: `conflict`, `removed` or `failed`.
  - `describeUnsaved(docs)`: “School/Biology” (changed on disk), …
- **The Editor and `useFileDocument` (grids, canvases)**: the flush saves straight away, ignoring the autosave delay. If the document changed while saving, it saves again (up to `SAVE_ATTEMPTS` = 3). Then it reports:
  - a conflict or removed banner (autosave is paused, so nothing is written);
  - a failed write;
  - otherwise `null`.
  - A conflict is never forced. The user picks a version with the banner's buttons.
- **One write at a time, for real:** `save()` in both used to wait for the write in flight only once. Two saves waiting for the same write (the blur save and install's flush) then both wrote, and the second's mtime check reported a false "changed on disk" conflict. Each now waits until no write is in flight, then checks the document still needs saving.
- **Embeds** register too. Their flush saves the block back into the source note.
  - If the source block changed elsewhere, the flush keeps the edit and reports a `conflict`; it does not reload over the edit as an ordinary autosave does. The embed's status reads "changed in the source — not saved".
  - When an embed closes with an edit, its final write (`writeBlock`, factored out of `save()`) rejects if the block changed or the write failed. The block's text then goes into a recovery file next to the source note.
- **`useUpdates.install()`**:
  1. Turns on `preserveEdits`, then makes `document.body` `inert` and blurs the focused element, so nothing new can be typed.
  2. Runs `saveAll()`.
  3. If anything is unsaved, it doesn't install. It restores the window and shows: _Not installed, so no edits are lost. Unsaved changes in “Welcome” (changed on disk). Resolve it, then try again._ This appears in the banner's alert and in Settings → Updates' status line.
  4. Otherwise it calls `updatesInstall` as before. If that fails, it restores the window and shows the error.
  - A second click while installing is ignored.
  - The install buttons (banner and Settings) prevent `mousedown`, so pressing one doesn't move focus. Moving focus would blur an embed and start its ordinary save before `preserveEdits` is on.
- **Shortcuts:** the global shortcut listener (`src/features/commands/Modals.tsx`, capture phase) swallows every key while `body` is `inert`. No command can change a note after the save.
- **No Rust change.**

## Review fixes (Codex, round 1)

1. An embed conflict during the flush no longer reloads over the edit; it is reported.
2. A flush that throws blocks the install.
3. A failed closing write is kept and retried, not forgotten.
4. An embed's closing write reports failure instead of resolving normally.

## Review fixes (Codex, round 2)

1. A save already under way (the blur save started by Install) no longer reloads over an embed edit: `preserveEdits` is checked when the conflict is found, not when the save started.
2. Failed writes are tracked one by one, not keyed by path. One embed's success can't settle another's failure, and a whole-file save settles only whole-file failures.
3. Failed writes are bound to their vault and only retried while that vault is open.

## Review fixes (Codex, round 3)

Retrying failed closing writes kept producing edge cases:

1. A later save "settled" content it never wrote.
2. A close during a save used a stale mtime and failed forever.
3. A retry could recreate a renamed or deleted file.

So retries were replaced by a recovery file, and `markSaved` and the `file`/`part` kinds are gone. Closing writes now wait for a save under way and use the current mtime (2).

## Review fixes (Codex, round 4)

1. Closing writes and recovery files are bound to the vault the document was loaded from, not the one open when it closes.
2. The install buttons prevent `mousedown`, so pressing one doesn't blur an embed before edits are protected.
3. Global shortcuts are ignored while the window is frozen.

## How to test

- `pnpm lint`, `pnpm typecheck`, `pnpm exec vitest run`.
- `src/features/updates/installGuard.test.tsx` covers:
  - an edit inside the autosave delay is on disk when the installer starts;
  - the window is `inert` while installing, and restored after an error;
  - a conflict blocks the install with a message naming the note. Disk and editor both keep their versions. After "Keep my version" the install goes ahead;
  - a failed write blocks the install;
  - the slow final write of a just-closed note is waited for;
  - saves queued behind a write in flight don't cause a false conflict;
  - a grid's pending change is saved;
  - a closed note's failed final write lands in a recovery file and the original is untouched. Two failures of one file get two files;
  - while no recovery file can be created, install is refused on every attempt, and goes ahead once one can;
  - a recovery file is never written while another vault is open;
  - closing a note while a save is under way writes the rest, with no false failure. This fails against the old closing write;
  - recovery-file naming;
  - a note closing after another vault was opened writes nothing into the new vault; back in its vault, the changes go into a recovery file;
  - the install button's mousedown is prevented;
  - a flush that throws counts as unsaved.
- `embeds.test.tsx`:
  - `saveAll` writes a pending embed edit back into the source note;
  - a changed source block is reported as a conflict, and both versions are kept;
  - a closed embed whose write-back can't happen keeps the block in a recovery file;
  - a save already under way when installing starts keeps the edit when the block changed. This test fails without `preservingEdits()`.
- `flows.test.tsx`: shortcuts do nothing while the window is inert.
- Each new test (closing-write vault, shortcuts, in-flight embed save, closing during a save) was checked to fail with its fix removed.

  3. Clicks Keep my version.
  4. Types again and installs straight away. It checks the edit is on disk when the development build's installer refusal appears.

## Known gaps

- **Closing the window** (not installing) still relies on the fire-and-forget unmount flush, so an edit inside the autosave delay may be lost on close. `saveAll()` is now available for a close-requested handler. This is a separate follow-up.
- **Embed conflicts outside installing:** when the source block changed elsewhere, an embed's ordinary autosave still reloads the block and drops the embed's edit. This is existing behaviour; only install's flush keeps the edit.
- **Recovery files** are new notes the user has to merge by hand. They hold a whole note, or just the block text for an embed. They are indexed like any note.
- **Switching away from a note with an open conflict banner** still drops the editor's version. That unmount skips the write, which is existing behaviour, and it doesn't involve installing. A follow-up could route it to a recovery file too.
