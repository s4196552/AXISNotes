# T-073 handoff: Installing an update never loses an edit

Found by Codex while reviewing T-072: "Install and restart" called the backend, which starts the installer and exits the app, without saving open documents. An edit inside the autosave delay was lost, and so was the editor's version of a note with an unresolved "changed on disk" conflict.

## What was built

- **`src/features/files/unsavedWork.ts`**, a registry of open documents:
  - `registerDocument(flush)`: each open note, grid, canvas and editable embed registers a function that saves now and reports what is still unsaved.
  - `trackClosingWrite(path, write)`: the final write a document makes when it closes (switching notes) is tracked, so it is waited for too.
  - `saveAll()`: runs every flush and waits for every tracked write. It returns the documents still not on disk, one per path, with a reason: `conflict`, `removed` or `failed`.
  - `describeUnsaved(docs)`: “School/Biology” (changed on disk), …
- **The Editor and `useFileDocument` (grids, canvases)**: the flush saves straight away, ignoring the autosave delay. If the document changed while saving, it saves again (up to `SAVE_ATTEMPTS` = 3). Then it reports:
  - a conflict or removed banner (autosave is paused, so nothing is written);
  - a failed write;
  - otherwise `null`.
  - A conflict is never forced. The user picks a version with the banner's buttons.
- **Embeds** register too. Their flush saves the block back into the source note.
- **`useUpdates.install()`**:
  1. Makes `document.body` `inert` and blurs the focused element, so nothing new can be typed.
  2. Runs `saveAll()`.
  3. If anything is unsaved, it doesn't install. It restores the window and shows: _Not installed, so no edits are lost. Unsaved changes in “Welcome” (changed on disk). Resolve it, then try again._ This appears in the banner's alert and in Settings → Updates' status line.
  4. Otherwise it calls `updatesInstall` as before. If that fails, it restores the window and shows the error.
  - A second click while installing is ignored.
- **No Rust change.**

## How to test

- `pnpm lint`, `pnpm typecheck`, `pnpm exec vitest run`.
- `src/features/updates/installGuard.test.tsx` covers:
  - an edit inside the autosave delay is on disk when the installer starts;
  - the window is `inert` while installing, and restored after an error;
  - a conflict blocks the install with a message naming the note. Disk and editor both keep their versions. After "Keep my version" the install goes ahead;
  - a failed write blocks the install;
  - the slow final write of a just-closed note is waited for;
  - a grid's pending change is saved.
  - Each of these tests fails against the old `install()`; the closing-write test fails without `trackClosingWrite`.
- `embeds.test.tsx`: `saveAll` writes a pending embed edit back into the source note.
- E2E: `pnpm e2e:build`, then `pnpm exec wdio run e2e/wdio.conf.ts --spec e2e/specs/updates.e2e.ts`. The new test "never installs over unsaved edits (T-073)":
  1. Makes a real conflict (types, then changes the file on disk).
  2. Checks the install is refused with the message, and that neither version is lost.
  3. Clicks Keep my version.
  4. Types again and installs straight away. It checks the edit is on disk when the development build's installer refusal appears.
  - Screenshot: `.agents/qa/updates/unsaved-conflict.png`.

## Known gaps

- **Closing the window** (not installing) still relies on the fire-and-forget unmount flush, so an edit inside the autosave delay may be lost on close. `saveAll()` is now available for a close-requested handler. This is a separate follow-up.
- **Embed conflicts:** when the source block changed elsewhere, an embed's save reloads the block and drops the embed's edit. This is existing behaviour, not changed here.
- **A failed final write of a closed document** blocks the install and is named, but its content can't be recovered: the editor is gone. The same failure already showed an error before this change.
