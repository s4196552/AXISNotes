# T-074 handoff: Never lose an edit on close, note switch or embed conflict

Follow-up to T-073 (installing an update saves everything first). This branch is based on `agent/claude/T-073`, which is approved but not merged. It covers the three remaining ways an edit could be lost.

## What was built

1. **Closing the window**
   - `src/features/files/closeGuard.ts`, started from `App.tsx` with `guardWindowClose()`. A close request (close button, Alt+F4) runs `saveBeforeExit()`:
     - freeze the window (`inert`, shortcuts off);
     - wait one macrotask for edits that blur commits;
     - `saveAll()`.
   - If nothing is unsaved, it closes with `backend.closeWindow()` (Tauri `destroy`; the capability adds `core:window:allow-destroy`).
   - Otherwise it unfreezes and stays open. The status bar reads: _Not closed, so no edits are lost. Unsaved changes in “Welcome” (changed on disk). Resolve it, or close again to quit without saving it._
   - A second close within `CLOSE_AGAIN_MS` (15 s) saves everything it can again, then quits even if something is still unsaved.
   - A close request while one is already saving is ignored. If `destroy` fails, the window unfreezes and shows why.
   - Backend API: `onCloseRequested(cb)` (the Tauri listener always calls `preventDefault`, so only `closeWindow` closes) and `closeWindow()`. The memory backend adds `requestClose()` and `windowClosed()` for tests.
   - `saveBeforeExit()` / `freezeEditing()` moved from `updates.ts` into the shared `src/features/files/beforeExit.ts`. Installing uses it unchanged.
2. **Switching away from a note with a conflict or "moved or deleted" banner**
   - The Editor's and `useFileDocument`'s closing write used to be skipped while paused, so the editor's version was dropped.
   - Now the closing write fails on purpose ("it changed on disk" / "it was moved or deleted"). `trackClosingWrite` then keeps the content in an `(unsaved …)` recovery file and says so.
   - The file on disk is untouched, and a deleted note isn't recreated. The recovery file sits next to the old path, recreating its folder if that is gone.
3. **Embed conflicts**
   - `EmbedController.save()` always keeps the edit when the source block changed. It shows "changed in the source — not saved" and **Reload from source** / **Keep mine** buttons in the embed header (`.cm-embed-actions`).
   - Keep mine (`overwriteBlock`) writes this version over the block as it is now.
   - If the block is gone from the source, it shows "no longer in the source — not saved" with only **Discard my edit**.
   - Until the user chooses, `saveAll` reports it as a conflict.
   - `preserveEdits` / `preservingEdits` and `save(keepOnConflict)` from T-073 are removed; preserving is now always on.
- Also: `trackClosingWrite`'s messages show an `Error`'s message without the `Error:` prefix.

## Review fixes (Codex, round 1)

1. "Keep mine", and an embed's ordinary save, pass the embed's own vault root, so the backend refuses them after a vault switch (T-073's `vault_root`).
2. A repeat conflict keeps the same buttons, so a blur save started by pressing one can't swap it out under the click. The buttons also prevent `mousedown`, so pressing one leaves focus in the embed.

## How to test

- `pnpm lint`, `pnpm typecheck`, `pnpm exec vitest run`.
- `closeGuard.test.tsx`:
  - close saves an edit in the autosave delay, then closes;
  - a conflict keeps the window open with the message, and the editor keeps its version;
  - closing again quits;
  - closing again right after resolving still saves the newest edit (a bug caught while writing the E2E);
  - after 15 s it asks again;
  - with nothing open it closes at once;
  - a failing `destroy` unfreezes the window and explains;
  - switching away from a conflicted note, a moved or deleted note, or a conflicted grid leaves a recovery file and doesn't touch the file on disk. These fail against the old unmount.
- `embeds.test.tsx`:
  - autosave and blur saves keep the edit on a conflict;
  - Keep mine writes over the changed block;
  - Reload from source drops the edit;
  - a gone block offers only Discard;
  - a second conflicting save keeps the same button, and its mousedown is prevented;
  - "Keep mine" is refused after another vault is opened.
- E2E: `pnpm e2e:build`, then `pnpm exec wdio run e2e/wdio.conf.ts --spec e2e/specs/close.e2e.ts`. WebDriver can't click the native close button, so the spec emits `tauri://close-requested`, the event Tauri sends when it is clicked, from the page. It checks:
  - a conflict keeps the window open, with the message and both versions intact (screenshot `.agents/qa/close/close-refused.png`);
  - after Keep my version and more typing, a close saves the edit and the window really closes (the WebDriver session ends, so the ERROR line in the log is expected).

## Known gaps

- **What Tauri does natively** (the close button sends the event; `has_js_listener` keeps the window open: tauri 2.11 `manager/window.rs:171`) was read in Tauri's source, not clicked in a test.
- **Killing the process** (Task Manager, shutdown without a close request) can still lose an edit in the 500 ms autosave delay.
- **Recovery files** for embeds hold only the block text.
