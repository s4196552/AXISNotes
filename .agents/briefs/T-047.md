## M2: native core

1. **Storage**: `library.json`, `device.json`, `backups/` under `AXIS_HUB_HOME` or
   `%LOCALAPPDATA%\AXIS\Hub\`, atomic writes, revisions, 10 rolling backups; sessions folder
   excluded from backups.
2. **Launch** (S2-D38): launch by item ID only; `.exe`-only `application` with argument arrays
   and detached creation flags; refuse script hosts and executable/script `file` targets;
   `.lnk`/file/folder through the OS opener (candidate: `tauri-plugin-opener`, record
   version/license); registered-URI allowlist with confirmation and the fixed denylist;
   http(s) validation. Metadata-only launch log (item ID, kind, time, result).
3. **Spike first**: two child webviews with different `data_directory` values on Windows
   (WebView2) — prove cookie isolation and record findings in docs/DECISIONS.md before the
   session UI contract is frozen. If isolation fails, stop and report to the lead.
4. **Sessions and remote tabs** (S2-D39): window `hub-window` hosting the trusted child
   webview `main` and sibling `site-<uuid>` child webviews. Requirements:
   - The one capability file sets `"webviews": ["main"]`, with `windows` omitted or empty, no
     `remote` and no wildcards. `windows` would cover every child webview in the window
     (https://v2.tauri.app/reference/acl/capability/).
   - Every command is declared in `build.rs` through `AppManifest::commands`, and each
     `allow-<command>` permission is granted explicitly to `main`. Undeclared custom commands
     are reachable by default (https://v2.tauri.app/security/capabilities/). Grant only the
     core/plugin permissions that have been reviewed.
   - Every handler guards on the invoking `tauri::Webview` label `main` and the app origin,
     never on the `Window` label.
   - `main` navigation is limited to the app origin.
   - Site navigation (initial URL, redirects, new windows) allows http(s) only and refuses
     reserved origins: `tauri://localhost`, `http(s)://tauri.localhost`, other `*.localhost`
     Tauri protocol hosts, and the configured `devUrl` origin.
   - New windows stay in the session, downloads are denied, and Clear session is available.

   No change to AXISNotes capabilities.
5. **External browsers and profiles** (S2-D40): detection of Edge/Chrome/Brave/Firefox install
   paths, read-only profile discovery, profile ID validation, per-kind argument templates
   (verify flags against vendor docs; cite them in docs/DECISIONS.md), default-browser open.
6. **Connect client** (S2-D42): vendored `axis-connect-client` using the launcher L1–L4 of
   S2-D07 (no spawn when Connect is alive; `revoked` needs an explicit "Pair again"); credential in keychain service
   `AXIS Hub` (memory keys with `AXIS_HUB_MEMORY_KEYS=1`); projects, members, federated
   search, resolve/open, apps list/approve/revoke, 15 s change polling, removing deleted
   project IDs from Hub items. Hub keeps working when Connect is absent. `search` merges a
   local `hub` group (section/item names, instant, no Connect needed) with Connect's groups;
   when Connect is unavailable the other apps appear as one explicit unavailable state.
7. **Axis-resource open fallback**: owner unavailable → offer "Start AXISNotes" via the user's
   configured Notes item, retry open for 15 s.
8. **Optional AI** (S2-D41): off by default; OpenAI-compatible Chat Completions only;
   execution evidence rules as S2-D31 (port or reimplement minimal probe; recorded fixtures);
   input minimisation; strict schema validation; returns suggestions only; `aiApply` accepts
   only a user-reviewed subset and uses the normal library mutations.

## Acceptance criteria

1. Launch fixture exe (built by T-049's probe or a unit-test helper) with args containing
   spaces, quotes, `&`, `|`, `%PATH%` and `-flag` → the child receives them verbatim (no shell).
2. `.bat`, `.cmd`, `.ps1` as application → refused; `.exe` given as `file` → refused;
   `ms-msdt:`/`search-ms:`/`file:` registration refused even with confirmation; unregistered
   scheme refused; `javascript:` and `http://user@host` websites refused.
3. Launching by item ID works after Hub restart; webview cannot pass a path/args to launch
   (no such command parameter exists; test the command signatures).
4. Two sessions: cookie set in session A is absent in session B; Clear session A removes it;
   "Open in browser" launches the configured browser/profile arguments (asserted via a fake
   browser exe that records argv).
5. Remote page in a site webview cannot call `__TAURI_INTERNALS__.invoke` for any Hub command
   and cannot reach Connect (403 unsigned); `main` refuses navigation to a remote URL.
   - **5a. Sibling child webviews.** With `main` and two site webviews open in `hub-window`,
     each site page invokes every command in the manifest list, plus representative
     plugin/core commands. Every call is denied, and state, launch log and probe output are
     unchanged. A Rust test using Tauri's mock runtime calls each handler directly with a
     webview labelled `site-x` in a window labelled `hub-window`, and gets `Forbidden`. That
     shows the guard holds even if the ACL were mis-scoped.
   - **5b. Custom invoke.** From a site page, raw IPC to every custom command fails,
     including one added only for the test without a manifest entry. A `fetch`/XHR `POST` to
     the IPC endpoint (`http://ipc.localhost/<command>`) with forged headers also fails. The
     capability-lint test fails when a command lacks a manifest entry or grant, or when a
     capability uses `windows`, `remote`, a wildcard or a label other than `main`.
   - **5c. Reserved-origin navigation.** A site webview is sent to each of these through
     `location`, a link click, a 302 from the fixture server and `window.open`:
     `tauri://localhost/`, `http://tauri.localhost/`, `https://tauri.localhost/`,
     `http://asset.localhost/`, the `devUrl` origin, `file:///C:/`, `data:text/html,x`,
     `javascript:1`, `blob:` and a custom scheme. Each is refused, and the webview stays on
     the fixture page. Saving a website item with any of these URLs is refused. `main`
     refuses every origin except the app origin.
6. Project create/update/delete via Connect with revisions; delete removes the ID from Hub items
   and leaves every Hub item and all launch mappings otherwise intact.
7. Connect absent/killed: library, launch and sessions still work; status shows unavailable.
8. AI suggestion with unknown field, unknown item ID, cycle, URL or path field → rejected;
   valid suggestion applies only the reviewed subset; no request made when AI is off; key never
   in settings file, logs or IPC payloads.
9. Library, device mappings and backups survive restart; sessions are not in backups.
