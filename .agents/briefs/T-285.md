# T-285: publish checks that survive a busy machine

The human asked to fix why tests were slow in the main checkout after the 0.3.112 publish stopped twice.

## Findings

- With every core in use, three different UI tests hit their 20 s limit on each of three full runs (400–466 s).
- The same commit passed in 105 s in a fresh checkout, then in 60 s in the main checkout itself, with nothing changed.
- Process sampling showed 14 test workers saturating the CPU and an idle Vitest main process, so the old worktrees weren't being scanned.
- The cause was load on the machine, not the checkout.

## Done when

- The publish script's test step tolerates load without hiding real failures.
