# T-162 review: Zen mode grab strip and Windows Snap

**Verdict: approve** (Claude self-review, 2026-11-04)

## What changed

- `src/app/zen.ts`: in Zen mode, a press on a title bar area (`data-tauri-drag-region`, the element itself, as Tauri checks) is handled by AXIS instead of Tauri's drag script. It uses a window capture listener and `stopImmediatePropagation`.
  - Moving 4 px (`DRAG_START`) with the button held starts a window drag. A full-screen window first leaves full screen, and is maximized if it wasn't already. Then `startDragging()` hands the press to Windows. Windows treats it as a maximized window's title bar drag, so it restores under the pointer and Snap applies.
  - A plain click does nothing.
  - A double-click restores (from full screen or maximized) or maximizes.
  - After a drag or double-click, the next pointer move hides the bar. Edges then stay quiet until the pointer has left them, so a snap that drops the pointer on the left edge doesn't slide the left panel in.
- `src/App.tsx` and `src/styles/app.css`: the new `.zen-drag-bar` strip is rendered only in Zen mode on the desktop.
  - It is 8 px tall, spans the top up to the window buttons, and has a small grab-handle pill.
  - It slides in with the tab row when the top edge is revealed.
  - While hidden it has `pointer-events: none`, so it can't take clicks from the note.
- `src/ipc/types.ts` and `src/ipc/tauriBackend.ts`: `WindowFrame` gains `isFullscreen` and `startDragging`. Both permissions were already granted: `core:default` and `allow-start-dragging`.
- Leaving Zen mode is unchanged. Once the window has been dragged out of full screen it stays a normal, maximized or snapped window, still in Zen mode, until Zen mode is toggled. Entering Zen mode again goes full screen.

## Findings

No blocking findings. Notes:

1. **Snap Layouts flyout on the maximize button: not done.** The flyout needs the window to answer `WM_NCHITTEST` with `HTMAXBUTTON` over the button, but the WebView covers the whole frameless window. Making it work would mean native subclassing in Rust, out of scope here. Win+Z still opens Snap Layouts for the window.
2. While snapped (not full screen), Zen mode keeps the bars hidden. Pressing the Zen button again then goes full screen, which undoes the snap. This is expected.
3. A double-click hides the bar on the next pointer move, even with the pointer still on the strip. Moving off the top edge and back reveals it again.

## Checked by hand in the built app (release exe, driven over the WebView2 DevTools port, no OS input)

Release `axisnotes.exe` from this branch was run with a scratch vault, config and WebView2 profile. Mouse events went through CDP `Input.dispatchMouseEvent`, and window state was read from Tauri's `is_fullscreen` and `is_maximized`.

| Step | Result |
| --- | --- |
| Zen on | full screen; strip at -8 px with `pointer-events: none`; `elementFromPoint` at y=3 is the page, not the strip |
| Pointer to y=2 | `data-zen-reveal="top"`; strip at 0, 8 px tall, `pointer-events: auto`; y=3 is the strip, y=20 the tab row |
| Press on strip, no move | still full screen |
| Move 10 px with button held | `fullscreen: false`, `maximized: true`, still Zen |
| Next move at y=1 | bar hidden (`reveal: null`) |
| Away and back to the top | revealed again |
| Double-click strip | restored (1280×820), then maximized again |
| Zen button on revealed row | Zen off |

A screenshot of the revealed strip was checked: the grab pill sits centred above the tab row.

**Not checked by me:** the real drag to a screen edge and the Snap result. The modal move loop needs a physical mouse button, and synthetic OS input is not allowed on this machine. The user is asked to try dragging the strip to the left or right edge in the published build.
