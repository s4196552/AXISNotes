# T-181 review: real OpenAI stream errors, a no-streaming retry, and GPT-6.1 Sol in the list

**Verdict: approve** (Claude self-review, 2026-11-07)

## Why

The user ran the Practice test skill with their OpenAI key and got "OpenAI (chat-latest): unexpected response: stream error". The local request log (metadata only) showed both tries failing the same way after 1.6 to 2.3 seconds: one with `gpt-6-sol`, one with `chat-latest`. The user also asked why GPT-6.1 Sol wasn't available.

- **Cause of the vague message:** OpenAI's stream `error` event can put its details in a nested `error` object (`{"type":"error","error":{"code","message","param"}}`). `openai_responses.rs` only read `message` at the top level, so every such failure became "stream error". The actual reason was dropped.
- **GPT-6.1 Sol:**
  - The built-in list (`ai-models.json`) only had GPT-6 Astra, Sol and Luna.
  - OpenAI's live list includes speech, image, embedding and old completion models, sorted only by id, so chat models were buried.
  - A model list that failed to load stayed cached for the whole session.

## What changed

- `codec/mod.rs`:
  - `stream_error` reads `message`, `code` and `param` from the top level, from `error`, and from `response.error`. The message becomes "<message> (<code>)". When there's no message at all, it says the stream stopped without giving a reason.
  - When a parameter is named, the error is `Invalid { param }`, so the adapter's existing drop-and-retry applies inside a stream too.
  - `stream_refused` recognises "can't stream this model" failures: `param: "stream"`, or a message about streaming plus verify, not supported, unsupported, not allowed or not permitted.
- `openai_responses.rs`: `response.failed`, `response.error` and `error` all go through `stream_error`.
- `adapter.rs` `stream`, only while nothing has reached the caller yet:
  - It drops a rejected parameter and retries, as before.
  - Then, if streaming was refused, it asks again as a plain request and passes the whole answer to the caller in one piece.
  - This doesn't apply to the ChatGPT plan, which must stream.
  - Other errors, such as quota, are not repeated.
- `registry.rs`:
  - For OpenAI, `is_text_model` hides embedding, tts, whisper, dall-e, moderation, transcribe, realtime, audio, babbage, davinci, sora and gpt-image models.
  - `order` lists models known to `ai-models.json` first, in the file's order, then the rest by id.
- `ai-models.json`: GPT-6.1 Sol (`gpt-6.1-sol`, vision, JSON, $2/$10). No context length, because I couldn't confirm it from OpenAI's own docs.
- `aiBlockStore.ts`: a model list that came back with an error, or failed outright, isn't cached, so the next time the picker opens it asks the provider again.
- `memoryAi.ts`: GPT-6.1 Sol in the browser preview's fake list.

## Findings

1. The exact reason the user's runs fail is still unknown until they run again on this build. The new message will name it, for example quota, an organisation that needs verification to stream, or the model not being available to the key. If it's the verification case, the no-streaming retry should make the run work. Otherwise the message says what to fix in their OpenAI account.
2. Whether `gpt-6.1-sol` appears in the picker depends on OpenAI's model list for the user's key. If the key's project can't use it, OpenAI won't list it. It's now near the top when it is listed.
